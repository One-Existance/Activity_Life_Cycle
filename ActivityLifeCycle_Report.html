1. Project Overview

This Android application was built to visually demonstrate every stage of the Android Activity Lifecycle in real time. Instead of just reading about onCreate, onStart, and friends in a textbook, a student can launch this app and watch each method fire — through on-screen Toast pop-ups and a persistent scrollable event log.

The app contains two Activities: a main screen with three interactive buttons, and a second screen that the user can navigate to and from. Switching between them triggers the pause/stop/restart chain, making all seven lifecycle callbacks observable without having to press the device's Home or Back buttons manually.

Key teaching goals of this app:
• Show all 7 lifecycle methods firing in order via Toast and a live log.
• Let the student trigger lifecycle transitions themselves using buttons.
• Demonstrate the difference between pausing (partial hide) and stopping (full hide).
• Show how onRestart works when returning to a stopped Activity.

3. What is the Android Activity Lifecycle?

An Activity is a single screen in an Android app. Android is a multi-tasking operating system — the user can receive calls, switch apps, rotate the screen, and press Back at any time. To manage all this, Android calls specific methods on your Activity at defined moments. These methods together form the Activity Lifecycle.

As a developer you override these methods to run your own code at the right moment — saving data before the app hides, releasing resources when the app closes, refreshing content when the app comes back to the foreground, and so on.

Complete Lifecycle Flow
onCreate() → onStart() → onResume()
↕
onPause() → onStop() → onDestroy()
↑
onRestart() → (goes back to onStart)

Arrow flows left-to-right on launch, right-to-left on exit.

Method When it is called Typical use
onCreate() The very first time the Activity is created. Set the layout, find views, set up button listeners.
onStart() Activity becomes visible to the user (but not yet interactive). Start animations or load data that must be visible.
onResume() Activity is in the foreground and fully interactive. Resume paused animations, start camera, register sensors.
onPause() Another activity comes partially in front (dialog, new screen starting). Pause animations, release camera, save draft data.
onStop() Activity is completely hidden (Home pressed, or another full-screen activity opened). Save persistent data, unregister broadcast receivers.
onRestart() Activity was stopped and the user is coming back to it. Refresh stale data, re-subscribe to data sources.
onDestroy() Activity is being permanently removed — Back pressed, or finish() called. Release all resources, close database connections.

4. AndroidManifest.xml — Explained

The AndroidManifest.xml is the configuration file for the entire app. Android reads it when it installs the app to understand what components exist (Activities, Services, etc.) and how to launch them. Every Activity you create must be declared here or Android will crash with an ActivityNotFoundException.

XML app/src/main/AndroidManifest.xml 
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">

    <application
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:theme="@style/Theme.ActivityLifeCycle">

        <activity
            android:name=".MainActivity"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>

        <activity
            android:name=".SecondActivity"
            android:exported="false" />

    </application>
</manifest>

<application>

Wraps all app-level settings. android:label sets the app name shown on the launcher icon. android:theme applies a visual style to every Activity by default.

<activity android:name=".MainActivity" android:exported="true">

Tells Android that MainActivity exists. The dot (.) before the name means it is in the root package (com.example.activitylifecycle). exported="true" means the system (launcher) is allowed to start it from outside the app.

<intent-filter>

This block marks MainActivity as the entry point of the app. action.MAIN = this is the main action; category.LAUNCHER = show it in the app drawer with an icon. Without this filter no launcher icon would appear.

<activity android:name=".SecondActivity" android:exported="false" />

Registers SecondActivity. exported="false" means only our own app can open it — no other app or the launcher can start it directly. It has no intent-filter because we start it manually with an Intent.

5. strings.xml — Explained

Instead of writing text directly inside layout files, Android best practice is to keep all user-facing strings in res/values/strings.xml. Layout files then reference them with @string/name and Java code uses getString(R.string.name). This also makes translation straightforward — you only touch one file.

XML app/src/main/res/values/strings.xml 
<resources>
    <string name="app_name">Activity Life Cycle</string>
    <string name="btn_open_second">Open Second Activity</string>
    <string name="btn_finish">Finish Activity (onDestroy)</string>
    <string name="btn_clear_log">Clear Log</string>
    <string name="label_lifecycle_log">Lifecycle Log:</string>
    <string name="log_placeholder">(events will appear here)\n</string>
    <string name="title_second_activity">Second Activity</string>
    <string name="btn_go_back">Go Back</string>
    <string name="toast_second_opened">SecondActivity opened — MainActivity is stopped</string>
</resources>

<string name="...">

Each entry pairs a key (the name attribute) with a value (the text inside the tag). The build system generates an integer ID for each name in the auto-generated R class, so R.string.btn_open_second is how Java code refers to it.

Referencing in XML layouts — @string/name

Inside any layout XML file, writing android:text="@string/btn_open_second" tells Android to look up that key at runtime and use its value. This means you can change the button label by editing strings.xml alone — no touching the layout file.

Referencing in Java — getString(R.string.name)

getString() is a method available on any Context (which Activity is). It looks up the string by its integer ID and returns it as a plain Java String. Used in SecondActivity to pass the Toast message.

Why not hardcode strings in the layout?

Android Lint flags hardcoded strings as warnings. More practically, if the same label appears in two places and you need to change it, you edit one line in strings.xml rather than hunting through multiple layout files.

LinearLayout — the root container

A LinearLayout stacks its children one after another. With orientation="vertical" they stack top-to-bottom. match_parent on both dimensions means it fills the whole screen. padding="16dp" adds breathing room around the edges.

android:id="@+id/btnOpenSecond"

The @+id/ prefix tells Android to create a new ID resource with this name in the R class. Java code later uses R.id.btnOpenSecond to find and get a reference to this exact button.

android:text="@string/btn_open_second"

Rather than hardcoding the label text directly, this references the string defined in strings.xml. Android resolves the value at runtime. All three buttons and the log label use this same pattern.

ScrollView with layout_height="0dp" and layout_weight="1"

Setting height="0dp" and weight="1" tells LinearLayout to give this view all remaining vertical space after the buttons above have taken their fixed height. The ScrollView then scrolls its content if it grows taller than the available space.

TextView id="tvLog" inside ScrollView

A ScrollView can only have one direct child. That child is a TextView whose text we append to from Java whenever a lifecycle method fires. fontFamily="monospace" gives the log a clean, readable appearance.

8. MainActivity.java — Explained

This is the brain of the app. It extends AppCompatActivity, overrides all seven lifecycle methods, sets up the three buttons, and maintains the on-screen log.

JAVA app/src/main/java/com/example/activitylifecycle/MainActivity.java 
package com.example.activitylifecycle;

import android.content.Intent;
import android.os.Bundle;
import android.widget.Button;
import android.widget.ScrollView;
import android.widget.TextView;
import android.widget.Toast;
import androidx.appcompat.app.AppCompatActivity;

public class MainActivity extends AppCompatActivity {

    private TextView tvLog;
    private ScrollView scrollView;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);

        tvLog      = findViewById(R.id.tvLog);
        scrollView = findViewById(R.id.scrollView);

        Button btnOpenSecond = findViewById(R.id.btnOpenSecond);
        Button btnFinish     = findViewById(R.id.btnFinish);
        Button btnClearLog   = findViewById(R.id.btnClearLog);

        btnOpenSecond.setOnClickListener(v ->
                startActivity(new Intent(this, SecondActivity.class)));

        btnFinish.setOnClickListener(v -> finish());

        btnClearLog.setOnClickListener(v ->
                tvLog.setText("(log cleared)\n"));

        log("onCreate", "Activity is being created");
        Toast.makeText(this, "onCreate: Activity created", Toast.LENGTH_SHORT).show();
    }

    @Override
    protected void onStart() {
        super.onStart();
        log("onStart", "Activity is becoming visible");
        Toast.makeText(this, "onStart: Activity visible", Toast.LENGTH_SHORT).show();
    }

    @Override
    protected void onResume() {
        super.onResume();
        log("onResume", "Activity is in the foreground");
        Toast.makeText(this, "onResume: Activity in foreground", Toast.LENGTH_SHORT).show();
    }

    @Override
    protected void onPause() {
        super.onPause();
        log("onPause", "Activity is partially hidden");
        Toast.makeText(this, "onPause: Activity partially hidden", Toast.LENGTH_SHORT).show();
    }

    @Override
    protected void onStop() {
        super.onStop();
        log("onStop", "Activity is no longer visible");
        Toast.makeText(this, "onStop: Activity not visible", Toast.LENGTH_SHORT).show();
    }

    @Override
    protected void onRestart() {
        super.onRestart();
        log("onRestart", "Activity is restarting after being stopped");
        Toast.makeText(this, "onRestart: Activity restarting", Toast.LENGTH_SHORT).show();
    }

    @Override
    protected void onDestroy() {
        super.onDestroy();
        Toast.makeText(this, "onDestroy: Activity is destroyed", Toast.LENGTH_SHORT).show();
    }

    private void log(String method, String description) {
        String entry = "[" + method + "]\n  → " + description + "\n\n";
        tvLog.append(entry);
        scrollView.post(() -> scrollView.fullScroll(ScrollView.FOCUS_DOWN));
    }
}

Line 1 — package com.example.activitylifecycle;

Declares which package this class belongs to. The package name is the unique identifier for the app on a device — no two installed apps can share the same package name. It must match the folder structure under src/main/java/.

Lines 3–9 — Import statements

Java requires you to import any class that lives outside your own file before you can use it. Key imports here:

  • Intent — the message object used to open SecondActivity.
  • Bundle — the data container Android passes to onCreate, holding saved state if the app was recreated.
  • Button, ScrollView, TextView — UI widget classes from android.widget.
  • Toast — the class that displays floating pop-up messages.
  • AppCompatActivity — the modern base class for Activities; provides backward-compatible toolbar and theme support.

Line 11 — public class MainActivity extends AppCompatActivity

extends AppCompatActivity means MainActivity inherits all the behaviour Android needs — it is already a fully functional Activity. We only override specific methods to add our own logic on top. Without extends AppCompatActivity, Android would not know how to manage this class as a screen.

Lines 13–14 — Instance fields

tvLog and scrollView are declared as class-level fields (not inside a method) because multiple lifecycle methods need to access them. If they were declared inside onCreate they would be destroyed when onCreate returns and would be unreachable in onStart, onResume, etc.

Line 17 — @Override

This annotation tells the compiler: "I am intentionally replacing a method that my parent class (AppCompatActivity) already has." It is not required but is strongly recommended — if you misspell the method name, the compiler will warn you instead of silently creating a new, never-called method.

Line 18 — protected void onCreate(Bundle savedInstanceState)

Bundle savedInstanceState is the data Android saves when the Activity is temporarily destroyed (e.g., on screen rotation) and then recreated. On first launch it is null. We do not use it here, but always pass it to super.onCreate().

Line 19 — super.onCreate(savedInstanceState);

Always the first line in any lifecycle override. It calls the parent class's implementation, which does essential internal setup (attaching the window, restoring state, etc.). Skipping it would crash the app.

Line 20 — setContentView(R.layout.activity_main);

Tells Android which XML layout to inflate and display as the screen. R.layout.activity_main is an auto-generated integer ID that maps to the file res/layout/activity_main.xml. This must be called before findViewById — otherwise the views do not exist yet.

Lines 22–26 — findViewById(...)

Searches the inflated layout tree for a view with the given ID and returns it. We immediately cast it to the correct type (TextView, ScrollView, Button). This is how Java code "connects" to the widgets defined in XML.

Lines 28–29 — Opening SecondActivity with an Intent

An Intent is a message object that describes an action to perform. new Intent(this, SecondActivity.class) creates an explicit Intent: "go to SecondActivity in this app." startActivity() hands it to Android, which creates and displays the new Activity. This also triggers onPause and onStop on MainActivity.

Line 31 — finish()

Programmatically tells Android to close and destroy this Activity. It is the code equivalent of pressing the Back button. Android will call onPause → onStop → onDestroy in sequence.

Lines 33–34 — Clearing the log

tvLog.setText("(log cleared)\n") replaces the entire text content of the log TextView with the placeholder message. This resets the visible log without affecting any lifecycle state.

Lines 40–78 — The six remaining lifecycle overrides

Each follows the exact same pattern:

  1. Call super.onXxx() first — always mandatory.
  2. Call our private log() helper to append to the on-screen log.
  3. Call Toast.makeText(this, "message", Toast.LENGTH_SHORT).show() to pop up a notification.

Note on onDestroy: We only show a Toast here (no log call) because by the time onDestroy fires, the Activity's view hierarchy may already be detached, making tvLog.append() unsafe. The Toast is queued by the system and still shows briefly.

Lines 81–85 — The log() helper method

A private utility method that keeps the lifecycle callbacks clean and DRY (Don't Repeat Yourself).

  • tvLog.append(entry) — adds text to the end of the existing text rather than replacing it, so the log builds up over time.
  • scrollView.post(() -> scrollView.fullScroll(ScrollView.FOCUS_DOWN)) — post() schedules a task on the main UI thread's message queue to run after the current layout pass completes. This ensures the new text has been measured and laid out before we attempt to scroll to the bottom. Without post() the scroll would happen before the new text is rendered and would land in the wrong position.
Why call super.onXxx() first?
The Android framework performs critical internal work inside these methods (managing window tokens, calling fragment lifecycle methods, etc.). If you call super after your own code, that internal work hasn't happened yet when your code runs, which can cause crashes or inconsistent state. The rule: always call super first in onCreate, onStart, onResume, onRestart. For onPause, onStop, onDestroy it is also safest to call super first.

9. SecondActivity.java — Explained

A deliberately minimal second screen. Its purpose is purely to give MainActivity somewhere to navigate to so that the pause/stop/restart cycle can be triggered by a button click rather than relying on pressing the physical Home key.

JAVA app/src/main/java/com/example/activitylifecycle/SecondActivity.java 
package com.example.activitylifecycle;

import android.os.Bundle;
import android.widget.Button;
import android.widget.Toast;
import androidx.appcompat.app.AppCompatActivity;

public class SecondActivity extends AppCompatActivity {

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_second);

        Button btnGoBack = findViewById(R.id.btnGoBack);
        btnGoBack.setOnClickListener(v -> finish());

        Toast.makeText(this,
            "SecondActivity opened — MainActivity is stopped",
            Toast.LENGTH_LONG).show();
    }
}

setContentView(R.layout.activity_second)

Loads and displays the blue second-screen layout. Each Activity must call this with its own layout file.

btnGoBack.setOnClickListener(v -> finish())

When the user taps "Go Back", finish() is called on SecondActivity. Android destroys SecondActivity and brings MainActivity back to the foreground, triggering onRestart → onStart → onResume on it.

Toast.LENGTH_LONG

Compared to LENGTH_SHORT (≈2 seconds), LENGTH_LONG displays the Toast for approximately 3.5 seconds. Used here because the message is more informative and we want the user to have time to read it.

10. User Interaction Flows

Here are the exact sequences of lifecycle callbacks that fire for each action a user can take:

Scenario A — App launched for the first time

onCreate → onStart → onResume

The Activity is created, becomes visible, then becomes fully interactive. All three fire in rapid succession.

Scenario B — "Open Second Activity" button tapped

onPause → onStop

MainActivity is pushed to the back stack. It pauses first (SecondActivity starts but hasn't fully appeared yet), then stops once SecondActivity is fully visible.

Scenario C — "Go Back" tapped in SecondActivity (or Back button pressed)

onRestart → onStart → onResume

onRestart is unique — it only fires when an Activity is returning from a stopped (not destroyed) state. It signals "you were here before and you're coming back."

Scenario D — "Finish This Activity" red button tapped

onPause → onStop → onDestroy

finish() is called, which triggers all three teardown methods. The Activity is permanently removed from memory. If the user returns to the app now, onCreate fires again from scratch.

Scenario E — Home button pressed

onPause → onStop

The Activity is hidden but not destroyed — Android keeps it in memory in case the user returns. Re-opening the app fires Scenario C (onRestart → onStart → onResume).
