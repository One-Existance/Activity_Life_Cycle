Android Activity Lifecycle

How and when Android calls each lifecycle method — with code

What is an Activity?

An Activity is a single screen in an Android app. Every screen the user sees is an Activity — the home screen, a settings screen, a login page. Each one is a Java class that extends AppCompatActivity.

Android is a multi-tasking system. At any point the user can receive a phone call, switch to another app, rotate the screen, or press Back. Android needs a way to tell your Activity what is happening so you can respond correctly — save data before hiding, free resources when closing, refresh content when coming back. It does this by calling a fixed set of methods on your Activity class at defined moments. These methods are the Activity Lifecycle.

The Lifecycle Flow

onCreate() → onStart() → onResume()
↓                                        ↑
onPause() → onStop() → onRestart()
↓
onDestroy()

Launch path: onCreate → onStart → onResume
Background path: onPause → onStop
Return path: onRestart → onStart → onResume
Close path: onPause → onStop → onDestroy

The 7 Lifecycle Methods

onCreate(Bundle savedInstanceState)
Fires once — when the Activity is first created.

This is where all setup happens: loading the layout with setContentView(), finding views with findViewById(), and wiring up button listeners. The Bundle parameter holds any previously saved state (e.g. from a screen rotation); it is null on first launch.

After this method returns, onStart() is always called next.

onStart()
Fires when the Activity is about to become visible to the user.

The Activity is not yet interactive — the user cannot tap anything yet. This is a good place to start animations or register for updates that need to be reflected on screen. It is called both on first launch (after onCreate) and when returning from a stopped state (after onRestart).

onResume()
Fires when the Activity is fully visible and interactive.

This is the running state — the user can see and touch the screen. The camera, sensors, or any resource that should only run while the app is in front of the user should be started here. Everything started in onResume should be stopped in onPause.

onPause()
Fires when another Activity is coming to the foreground.

The Activity is still partially visible (for example, a dialog or a translucent Activity is in front). This method must run fast — Android will not move on to the next Activity until it returns. Use it to pause animations and save anything that must be persisted immediately. Do not do heavy work here.

If the user returns to the Activity, onResume is called. If the user navigates further away, onStop follows.

onStop()
Fires when the Activity is completely hidden from the user.

The user has either switched to another app, pressed Home, or opened a new full-screen Activity on top. The Activity is no longer visible at all. This is where you release resources that are not needed while the app is in the background — unregister broadcast receivers, stop music playback, save data to a database.

The Activity object still exists in memory. If the user comes back, onRestart is called. If the system needs memory or the user presses Back, onDestroy follows.

onRestart()
Fires when a stopped Activity is about to come back to the screen.

This method is unique — it only fires when an Activity is coming back from a stopped state, not from a destroyed state. It is always followed immediately by onStart(). Use it to refresh data that may have changed while the app was in the background.

onDestroy()
Fires when the Activity is being permanently removed.

This happens when the user presses Back, when finish() is called in code, or when the system kills the Activity to free memory. After this method the Activity object is gone. Release any remaining resources — close database connections, cancel network requests, stop threads.

Note: this is not guaranteed to be called if the system kills the process forcefully. Never rely on it as the only place to save critical data — use onPause or onStop for that.

How It Looks in Code

Each lifecycle method is overridden in the Activity class. The @Override annotation marks that we are replacing a method from the parent class (AppCompatActivity). The first line inside every override must be a call to super.onXxx() so that the Android framework can do its own internal work first. Our logic goes after that.

In this app, each method calls a private log() helper that appends a line to the on-screen log, and shows a Toast pop-up so the event is visible immediately.

MainActivity.java — lifecycle methods
@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);
    // view setup and button wiring happens here
    log("onCreate", "Activity is being created");
    Toast.makeText(this, "onCreate: Activity created", Toast.LENGTH_SHORT).show();
}

@Override
protected void onStart() {
    super.onStart();
    log("onStart", "Activity is becoming visible");
    Toast.makeText(this, "onStart: Activity visible", Toast.LENGTH_SHORT).show();
}

@Override
protected void onResume() {
    super.onResume();
    log("onResume", "Activity is in the foreground");
    Toast.makeText(this, "onResume: Activity in foreground", Toast.LENGTH_SHORT).show();
}

@Override
protected void onPause() {
    super.onPause();
    log("onPause", "Activity is partially hidden");
    Toast.makeText(this, "onPause: Activity partially hidden", Toast.LENGTH_SHORT).show();
}

@Override
protected void onStop() {
    super.onStop();
    log("onStop", "Activity is no longer visible");
    Toast.makeText(this, "onStop: Activity not visible", Toast.LENGTH_SHORT).show();
}

@Override
protected void onRestart() {
    super.onRestart();
    log("onRestart", "Activity is restarting after being stopped");
    Toast.makeText(this, "onRestart: Activity restarting", Toast.LENGTH_SHORT).show();
}

@Override
protected void onDestroy() {
    super.onDestroy();
    Toast.makeText(this, "onDestroy: Activity is destroyed", Toast.LENGTH_SHORT).show();
}
Why super.onXxx() must come first: the parent class does critical internal work inside these methods — attaching windows, managing fragments, restoring state. Calling your own code before super means that infrastructure hasn't been set up yet, which can cause crashes or broken behaviour.

What Fires in Each Situation

App launched for the first time

onCreate → onStart → onResume

User opens another app or presses Home

onPause → onStop

User comes back to the app after pressing Home

onRestart → onStart → onResume

User presses Back / finish() is called

onPause → onStop → onDestroy

A dialog or translucent Activity appears on top

onPause — Activity is still partially visible, onStop does NOT fire

Screen is rotated

onPause → onStop → onDestroy → onCreate → onStart → onResume

Android destroys and recreates the Activity on rotation so the layout can be reloaded for the new orientation. The Bundle savedInstanceState in onCreate is how data survives this.
